# TypeScript GraphQL Schema 构建选型对比 (2026)

这是一个用于横向对比 2026 年主流 TypeScript GraphQL Schema 构建库的示例项目。我们通过实现一个相同的业务场景——**“极简在线咖啡点餐系统”**，来评估不同工具的开发效率（DX）、类型安全性和样板代码量。

## ☕ 业务模型：咖啡点餐系统

每个库都必须实现以下核心领域模型和完整的 CRUD 操作：

### 领域模型

- **User**: 用户信息（id, name, email）。
- **Food**: 菜单项接口（Interface），定义公共字段（id, name, price）。
- **Coffee**: 咖啡类型，实现 `Food` 接口，特有属性：
  - `sugarLevel`（含糖量枚举：NONE | LOW | MEDIUM | HIGH）
  - `origin`（产地字符串，如 "Colombia", "Ethiopia"）
- **Dessert**: 点心类型，实现 `Food` 接口，特有属性：
  - `calories`（卡路里，浮点数）
- **MenuItem**: 联合类型（Union），`MenuItem = Coffee | Dessert`，用于展示各库对 Union 类型的支持。
- **Order**: 订单信息（id, createdAt, status, userId, itemIds）。
  - `status` 枚举：PENDING | COMPLETED | CANCELLED
  - 创建时默认状态为 `PENDING`

### Query（查询）

#### User 模块
- `users: [User!]!` - 查询所有用户
- `user(id: Int!): User!` - 根据 ID 查询用户，用户不存在时返回错误信息 "User not found"
- `User.orders: [Order!]!` - 关联查询：获取用户的所有订单（通过 userId 关联）

#### Menu 模块
- `menu: [MenuItem!]!` - 查询所有菜单项（返回 Union 类型）
  - 必须支持内联片段（Inline Fragments）查询特有字段：
    - `... on Coffee { sugarLevel, origin }`
    - `... on Dessert { calories }`
  - 返回的数据必须包含 `__typename` 字段用于类型区分
- `menuItem(id: Int!): MenuItem` - 根据 ID 查询菜单项（返回 Union 类型，支持内联片段）

#### Order 模块
- `orders: [Order!]!` - 查询所有订单
- `order(id: Int!): Order` - 根据 ID 查询订单
- `Order.user: User` - 关联查询：获取订单的下单人信息（通过 userId 关联）
- `Order.items: [MenuItem!]!` - 关联查询：获取订单内的商品详情
  - 返回 Union 类型，必须支持内联片段查询特有字段
  - 通过 itemIds 数组关联查询对应的菜单项

### Mutation（变更）

#### User 模块
- `createUser(name: String!, email: String!): User!` - 创建用户
  - 邮箱格式验证：email 必须包含 `@` 符号，否则返回错误信息（包含 "email" 关键词）
- `updateUser(id: Int!, name: String, email: String): User!` - 更新用户
  - `name` 和 `email` 为可选参数
- `deleteUser(id: Int!): User` - 删除用户，返回被删除的用户信息

#### Menu 模块
- `createCoffee(name: String!, price: Float!, sugarLevel: SugarLevel!, origin: String!): Coffee!` - 创建咖啡
  - 返回的 Coffee 对象必须包含 `__typename: "Coffee"` 字段
- `updateCoffee(id: Int!, name: String, price: Float, sugarLevel: SugarLevel, origin: String): Coffee` - 更新咖啡
  - 所有字段均为可选参数
  - 如果 ID 对应的不是 Coffee 类型，应返回 null 或错误
- `createDessert(name: String!, price: Float!, calories: Float!): Dessert!` - 创建点心
  - 返回的 Dessert 对象必须包含 `__typename: "Dessert"` 字段
- `updateDessert(id: Int!, name: String, price: Float, calories: Float): Dessert` - 更新点心
  - 所有字段均为可选参数
  - 如果 ID 对应的不是 Dessert 类型，应返回 null 或错误
- `deleteMenuItem(id: Int!): MenuItem` - 删除菜单项（返回 Union 类型）

#### Order 模块
- `createOrder(userId: Int!, items: [Int!]!): Order!` - 创建订单
  - 业务验证（必须全部通过）：
    1. `items` 数组不能为空，否则返回错误信息（包含 "At least one item is required"）
    2. `userId` 必须在数据库中存在，否则返回错误信息（包含 "User not found"）
    3. `items` 数组中的所有 `itemId` 都必须在数据库中存在，否则返回错误信息（包含 "Menu item not found"）
  - 创建成功时，订单状态默认为 `PENDING`
- `updateOrder(id: Int!, status: OrderStatus!): Order` - 更新订单状态
- `deleteOrder(id: Int!): Order` - 删除订单，返回被删除的订单信息

### 技术要求

1. **Union 类型支持**：
   - 必须正确返回 `__typename` 字段
   - 必须支持内联片段查询特有字段
   - 在 resolver 中需要根据 `__typename` 进行类型区分

2. **Interface 支持**：
   - `Coffee` 和 `Dessert` 必须实现 `Food` 接口
   - 接口的公共字段（id, name, price）会自动继承，无需重复定义

3. **关联查询**：
   - 支持通过关联字段（如 `User.orders`、`Order.user`、`Order.items`）进行关联查询
   - 关联查询应能正确处理 Union 类型

4. **错误处理**：
   - 查询不存在的资源时应返回明确的错误信息
   - 业务验证失败时应返回描述性的错误信息

## 📐 对比维度解析

在评估 GraphQL Schema 构建库时，我们主要关注以下 5 个核心技术维度。这些维度直接影响开发者的编码体验（DX）、代码的可维护性以及运行时的性能。

### 1. 架构模式
架构模式决定了代码的组织方式以及 Schema 的构建逻辑，是选型时最先需要考虑的因素。
- **定义**：库是如何将 TypeScript 代码转换为 GraphQL Schema 的。
  - **Decorator (装饰器)**：使用类和装饰器来定义类型，依赖反射元数据。
  - **Builder (构建器)**：使用函数式 API 显式构建类型定义。
  - **Weaving (编织)**：通过组合独立的 Resolver 和 Schema 定义来构建，通常与推断结合。
  - **Inference (自动推断)**：直接分析 TypeScript 类型定义生成 Schema，追求零配置。
  - **Schema 构建**：将定义的类型和 Resolver 组装成可执行的 GraphQL Schema 实例的过程。不同的架构模式对应不同的构建方式，如 `buildSchema()`（装饰器）、`builder.toSchema()`（构建器）、`weave()`（编织）或静态分析工具（推断）。

- **得分点 (Scoring Points)**：
  - **依赖复杂度 (Dependency Complexity)**：
    - ⭐️⭐️⭐️⭐️⭐️: **极简依赖**。仅依赖 `graphql` 标准库，零运行时开销，无额外第三方依赖。
    - ⭐️⭐️⭐️⭐️: **轻量依赖**。运行时依赖极少（1-2个），主要用于类型增强或轻量辅助。
    - ⭐️⭐️⭐️: **中等依赖**。需要引入反射库（`reflect-metadata`）或多个验证库（`class-validator` 等）。
    - ⭐️⭐️: **重度依赖**。依赖较多第三方库，甚至包含完整的构建编译器。
    - ⭐️: **臃肿依赖**。强制捆绑大量框架和工具（10+ 个运行时依赖），严重增加包体积。
  
  - **构建流程 (Build Flow)**：
    - ⭐️⭐️⭐️⭐️⭐️: **即写即用**。纯运行时构建，无需任何代码生成（CodeGen）或专门的 CLI 构建步骤。
    - ⭐️⭐️⭐️⭐️: **轻量构建**。支持运行时，但通常建议配合一个简单的类型生成步骤以获得最佳 TS 体验。
    - ⭐️⭐️⭐️: **显式构建**。必须运行 CLI 命令生成 Schema 文件或类型定义，代码才能通过编译或运行。
    - ⭐️⭐️: **黑盒构建**。依赖专有编译器或复杂的代码注入转换，构建过程不透明，调试困难。
    - ⭐️: **封闭构建**。强绑定专属 CLI 和构建工具，无法集成到现有的打包工具（如 Vite, Rspack）中。
  
  - **配置魔法 (Config & Language Magic)**：
    - ⭐️⭐️⭐️⭐️⭐️: **零魔法**。不依赖装饰器、反射元数据或非标准 TS 语法，完全符合原生 TS 最佳实践。
    - ⭐️⭐️⭐️⭐️: **极简配置**。仅需少量符合直觉的配置，主要依靠 TS 自身的类型推断。
    - ⭐️⭐️⭐️: **特性依赖**。必须启用 TS 实验性特性（如 `experimentalDecorators`）并手动配置反射环境。
    - ⭐️⭐️: **深度注入**。通过编译器插件进行大规模代码修改或元数据注入。
    - ⭐️: **强力魔改**。强制使用自定义转换逻辑，用户完全失去对最终生成的 Schema 的控制。

  - **生态集成 (Ecosystem Integration)**：
    - ⭐️⭐️⭐️⭐️⭐️: **完全中立**。支持标准 `npm install`，可自由搭配任何 Web 框架和打包工具。
    - ⭐️⭐️⭐️⭐️: **良好集成**。标准安装流程，对主流 GraphQL Server 和打包工具有优秀的适配性。
    - ⭐️⭐️⭐️: **环境敏感**。虽然可安装，但对运行环境有特殊要求（如必须配置反射环境或装饰器）。
    - ⭐️⭐️: **安装受限**。只能通过官方模板创建项目，无法直接安装到现有工程中。
    - ⭐️: **强框架绑定**。强制绑定特定 Web 框架（如 Hono），无法灵活更换底层驱动或集成到其他生态。

### 2. 类型定义
类型定义是 Schema 构建的核心，决定了 TypeScript 类型与 GraphQL 类型映射的深度与效率。

#### 🎯 评判得分点

**单一数据源（Single Source of Truth）实现度**
*   **⭐️⭐️⭐️⭐️⭐️**：极致统一。从一份定义同时生成 TypeScript 类型、运行时验证逻辑（如 Zod/Valibot）和 GraphQL Schema，彻底消除同步成本。
*   **⭐️⭐️⭐️⭐️**：深度推断。核心定义即 Schema，另一方（TS 或 Schema）通过类型工具或 JSDoc 自动提取，仅需极少辅助配置。
*   **⭐️⭐️⭐️**：逻辑关联。TS 类型与 Schema 定义通过装饰器等方式绑定，虽存在少量重复但能维持类型链路。
*   **⭐️⭐️**：弱同步。依赖代码生成（Code-Gen）在物理文件间同步类型，修改后需运行构建命令才能更新。
*   **⭐️**：完全手动。TS 类型与 GraphQL 定义互不感知，需手动维护两套定义，极易出现不一致。

**枚举与字符串联合支持（Enum & String Union Types）**
*   **⭐️⭐️⭐️⭐️⭐️**：零配置复用。直接支持 TypeScript 原生 `enum` 或字符串联合类型（`'A' | 'B'`），无需任何手动注册。
*   **⭐️⭐️⭐️⭐️**：轻量映射。支持通过简单的 API 映射 `as const` 数组或对象，无需重定义成员名称。
*   **⭐️⭐️⭐️**：显式注册。需调用特定函数（如 `registerEnumType`）手动注册，但在推断中能保持类型安全。
*   **⭐️⭐️**：重复声明。需在库提供的 DSL 中完全重写枚举成员，导致字符串字面量在多处硬编码。
*   **⭐️**：映射缺失。无法有效映射 TS 枚举，需手动处理原始值到 GraphQL 枚举的映射逻辑。

**接口继承与联合类型体验（Interface & Union）**
*   **⭐️⭐️⭐️⭐️⭐️**：全自动决议。接口字段自动继承；联合类型自动处理 `__typename`（如通过辨别式联合或字段特征识别）。
*   **⭐️⭐️⭐️⭐️**：智能继承。支持字段继承，但 Union 类型的决议可能需要简单的元数据标记或显式的 `__typename` 字面量。
*   **⭐️⭐️⭐️**：逻辑决议。支持抽象类型，但需要手动实现 `resolveType` 函数，且对原始数据结构有特定依赖。
*   **⭐️⭐️**：手动补全。实现接口时必须手动重复声明所有公共字段；Union 成员需在 Resolver 中手动返回类型名称。
*   **⭐️**：基本模拟。缺乏抽象类型的原生封装，仅能通过普通对象和过程式逻辑模拟接口或联合行为。

**类型推断强度与显式声明平衡**
*   **⭐️⭐️⭐️⭐️⭐️**：原生分析。直接分析 TS 源码（类/接口），自动推断基础类型、数组及可空性，几乎无显式声明负担。
*   **⭐️⭐️⭐️⭐️**：强大推断。Builder API 能自动推导绝大部分类型，仅在循环引用或复杂嵌套时需少量显式标注。
*   **⭐️⭐️⭐️**：按需标注。基础类型可推断，但数组、Promise 及延迟加载类型频繁需要 `() => Type` 语法。
*   **⭐️⭐️**：强力绑定。每个字段、参数及返回值都必须通过装饰器或泛型手动指定类型，推断能力受限。
*   **⭐️**：零推断。完全依赖手动显式映射，开发者必须为每一处代码手动配置对应的 GraphQL 类型元数据。

### 3. 解析器定义与输入验证
解析器（Resolver）是业务逻辑的核心所在。优秀的解析器定义应当能够自动推断输入参数类型、提供强类型的返回值校验，并能优雅地集成验证逻辑。

#### 3.1 开发体验（代码简洁度）
评估定义完整的领域模块（包含 Query、Mutation、Field Resolver）所需的代码量和模板代码量。

- **⭐⭐⭐⭐⭐**：代码极简，几乎无样板代码，类型定义与 Resolver 合一，链式 API 直观
- **⭐⭐⭐⭐**：代码简洁，模板代码量中等，需要少量装饰器、配置或注释，代码结构清晰
- **⭐⭐⭐**：代码量中等，模板代码较多，需要额外的 API 包装
- **⭐⭐**：代码冗长，大量模板代码，需要装饰器或配置对象
- **⭐**：代码非常冗长，大量重复的模板代码

#### 3.2 模块化设计（领域驱动开发支持）
评估库是否支持按领域模块组织代码，以及是否强制模块化。

- **⭐⭐⭐⭐⭐**：天然领域模块化，强制按领域组织，类型定义、Query、Mutation、Field Resolver 都在同一模块中，通过领域边界（如 Resolver 类或对象）创建明确的模块边界
- **⭐⭐⭐⭐**：支持领域模块化，提供了模块化 API，但不强制模块化，可以按领域拆分文件，需要开发者自觉遵守
- **⛔**：无模块化考虑，完全按操作类型隔离接口，完全按操作类型（Query/Mutation）组织，需要手动合并数组或对象，容易写出耦合的巨型文件

#### 3.3 参数定义与类型推导
评估参数定义的简洁性和类型推导的完整性。

- **⭐⭐⭐⭐⭐**：参数类型完全自动推断，无需手动声明，IDE 提示完善。支持链式 API 或函数参数自动推断，类型从 Schema 定义自动推导
- **⭐⭐⭐⭐**：参数类型大部分自动推断，少量需要显式声明。通过 Builder API 或类型推断工具自动推导，需要少量类型注解
- **⭐⭐⭐**：参数类型需要部分显式声明，但类型安全。需要手动类型声明，但 TypeScript 可以理解参数类型
- **⭐⭐**：参数类型需要大量显式声明，类型推导有限。每个参数都需要装饰器或配置对象显式声明类型
- **⛔**：无类型推导，需要完全手动声明所有参数类型

#### 3.4 输入验证机制
评估格式验证和自定义验证的能力，以及验证与 Schema 定义的集成程度。

- **⭐⭐⭐⭐⭐**：声明式验证，验证逻辑与 Schema 定义完全合一，支持格式验证（如 `z.email()`）和自定义验证（如 `.refine()`），自动验证，无需额外插件
- **⭐⭐⭐⭐**：支持声明式验证，但需要额外配置。使用装饰器或插件提供验证功能，需要参数类型类或插件配置
- **⭐⭐⭐**：支持验证，但需要手动编写验证逻辑。需要手动调用验证函数，验证代码和业务逻辑混合
- **⭐⭐**：无内置验证，需要完全手动实现。所有验证逻辑都需要在 Resolver 中手动编写，验证代码重复
- **⛔**：无任何验证支持，无法进行输入验证

#### 3.5 批量加载（DataLoader）集成
评估批量加载功能的支持程度和样板代码量。

- **⭐⭐⭐⭐⭐**：原生内置支持，无缝调用 dataloader，几乎没有样板代码。只需定义 `.load()` 或 `load` 函数，无需配置 Context 或创建 DataLoader 实例
- **⭐⭐⭐⭐**：通过插件或其他形式支持 dataloader，需要一些样板代码。需要安装插件和配置，使用声明式 API（如 `t.loadableGroup()`）
- **⛔**：没有提供任何内置的 dataloader 支持，需要大量 context 样板代码和 dataloader 样板代码。需要手动创建 DataLoader 实例、定义 Context 类型、配置 Context 注入，样板代码很多

### 4. 内置功能
内置功能决定了库在应对复杂业务场景时的"开箱即用"能力。
- **定义**：库是否原生支持 GraphQL 开发中的常见模式和进阶功能，减少样板代码（Boilerplate）。功能不应只是简单的堆砌，而应与核心 API 深度集成并保持类型安全。现代库应当通过灵活的插件系统（Plugin System）提供功能，既能避免核心库过于臃肿，又能显著减少开发者编写重复性逻辑的工作量。

#### 🎯 评判得分点

**指令支持（Directives）**
- **✅ 内置支持**：原生支持定义和使用 GraphQL Directives，支持联邦架构 (Federation)，API 简洁且类型安全。
- **⚠️ 插件/额外实现**：不内置支持，但可通过官方插件、社区插件或手动实现 Directives 功能，需要额外配置和样板代码。
- **⛔ 无法实现**：完全不支持 Directives 定义，无法通过任何方式实现 Directives 功能。

**扩展支持（Extensions）**
- **✅ 内置支持**：原生支持 GraphQL Extensions 的定义和使用，能够声明查询复杂度（complexity）、执行时间等扩展信息，API 直观。
- **⚠️ 插件/额外实现**：不内置支持，但可通过插件或手动扩展 Context 来实现类似功能，需要额外配置。
- **⛔ 无法实现**：完全不支持 Extensions，无法扩展 GraphQL 执行上下文。

**批量加载（DataLoader）集成**
- **✅ 内置支持**：原生内置 DataLoader 支持，无缝调用，几乎没有样板代码。只需定义 `.load()` 或 `load` 函数，无需配置 Context 或创建 DataLoader 实例。
- **⚠️ 插件/额外实现**：通过插件或其他形式支持 dataloader，需要一些样板代码。需要安装插件和配置，使用声明式 API（如 `t.loadableGroup()`）。
- **⛔ 无法实现**：没有提供任何内置的 dataloader 支持，且无法通过插件实现，需要大量 context 样板代码和 dataloader 样板代码。

**自定义标量（Scalars）**
- **✅ 内置支持**：内置了常用的标量类型（如 `DateTime`, `JSON`, `BigInt`, `Date` 等），定义新标量类型简便，API 直观且类型安全。
- **⚠️ 插件/额外实现**：不内置常用标量，但可通过插件或手动定义实现自定义标量，需要额外配置和样板代码。
- **⛔ 无法实现**：完全不支持自定义标量类型，只能使用 GraphQL 标准标量类型。

**订阅（Subscription）**
- **✅ 内置支持**：原生支持 GraphQL Subscriptions，支持实时数据推送，底层传输协议兼容性好（WebSocket, SSE 等），API 简洁。
- **⚠️ 插件/额外实现**：不内置支持，但可通过插件或集成第三方库（如 `graphql-subscriptions`）实现订阅功能，需要额外配置。
- **⛔ 无法实现**：完全不支持 Subscriptions，无法实现实时数据推送功能。

**上下文（Context）注入**
- **✅ 内置支持**：原生支持在 Resolver 中注入上下文，上下文的类型推导完善，IDE 提示良好，无需手动类型声明。
- **⚠️ 插件/额外实现**：不内置支持，但可通过插件或手动扩展实现上下文注入，需要手动定义 Context 类型和注入逻辑。
- **⛔ 无法实现**：完全不支持上下文注入，无法在 Resolver 中访问请求级别的上下文信息。

**中间件（Middleware）**
- **✅ 内置支持**：原生支持在 Resolver 执行前后注入中间件逻辑（如日志记录、权限检查、性能监控），API 简洁，支持链式调用。
- **⚠️ 插件/额外实现**：不内置支持，但可通过插件或手动包装 Resolver 实现中间件功能，需要额外配置和样板代码。
- **⛔ 无法实现**：完全不支持中间件机制，无法在 Resolver 执行前后注入逻辑。

**查询复杂度分析（Query Complexity）**
- **✅ 内置支持**：原生支持查询复杂度计算和分析，能够自动或声明式地计算查询复杂度，防止复杂查询攻击。
- **⚠️ 插件/额外实现**：不内置支持，但可通过插件或手动实现复杂度分析，需要额外配置和自定义逻辑。
- **⛔ 无法实现**：完全不支持查询复杂度分析，无法防止复杂查询攻击。

**深度限制（Depth Limiting）**
- **✅ 内置支持**：原生支持查询深度限制，能够自动限制查询嵌套深度，防止深度查询攻击。
- **⚠️ 插件/额外实现**：不内置支持，但可通过插件或手动实现深度限制，需要额外配置。
- **⛔ 无法实现**：完全不支持深度限制，无法防止深度查询攻击。

### 5. 生态集成
生态集成衡量了库在整个 TypeScript 工具链中的协作能力，是决定项目长期可维护性的关键。
- **定义**：库与 TypeScript 生态中其他常用工具的互操作性。优秀的集成应当能够消除"胶水代码"，构建端到端的类型安全链路。它应当是轻量且非侵入式的，允许开发者根据业务需求自由组合最佳实践工具栈。

#### 🎯 评判得分点

**ORM 集成深度（ORM Integration Depth）**
- **⭐️⭐️⭐️⭐️⭐️**：**深度整合**。提供官方插件直接复用 ORM 模型定义（如 Prisma, Drizzle, TypeORM），自动生成高效的数据库查询，类型完全同步，零样板代码。
- **⭐️⭐️⭐️⭐️**：**良好集成**。提供官方或社区插件支持主流 ORM，能够复用模型定义，但需要少量配置，类型同步良好。
- **⭐️⭐️⭐️**：**基础集成**。支持通过插件或手动方式集成 ORM，能够复用部分模型定义，但需要较多配置和样板代码。
- **⭐️⭐️**：**弱集成**。仅能通过手动方式集成 ORM，需要大量胶水代码，类型同步需要手动维护。
- **⭐️**：**无集成**。完全不支持 ORM 集成，必须手动编写所有数据库查询逻辑。

**验证库集成（Validation Library Integration）**
- **⭐️⭐️⭐️⭐️⭐️**：**无缝集成**。原生支持主流验证库（Zod, Valibot, Yup 等），验证逻辑与 Schema 定义完全合一，从验证规则自动推导类型，零配置。
- **⭐️⭐️⭐️⭐️**：**深度集成**。通过官方插件支持主流验证库，验证逻辑与 Schema 定义深度绑定，类型推导良好，需要少量配置。
- **⭐️⭐️⭐️**：**基础集成**。支持通过插件集成验证库，能够使用验证规则，但需要手动同步类型，需要中等配置。
- **⭐️⭐️**：**弱集成**。仅能通过手动方式使用验证库，验证逻辑与 Schema 定义分离，需要大量样板代码。
- **⭐️**：**无集成**。完全不支持验证库集成，必须手动编写所有验证逻辑。

**GraphQL Server 兼容性（Server Compatibility）**
- **⭐️⭐️⭐️⭐️⭐️**：**完全兼容**。与所有主流 GraphQL Server（Apollo Server, GraphQL Yoga, Envelop, Hono 等）完全兼容，提供官方适配器，零配置即可使用。
- **⭐️⭐️⭐️⭐️**：**标准兼容**。与标准 GraphQL.js 兼容，可以集成到主流 Server，但需要手动适配，需要中等配置。
- **⭐️**：**绑定特定 Server**。强制绑定特定 GraphQL Server，无法集成到其他 Server。

**Web 框架适配（Web Framework Adapter）**
- **⭐️⭐️⭐️⭐️⭐️**：**全框架支持**。提供官方适配器支持主流 Web 框架（Express, Fastify, Next.js, Hono, Koa 等），集成简单，类型安全。
- **⭐️⭐️⭐️⭐️**：**主流框架支持**。支持大部分主流 Web 框架，提供官方或社区适配器，需要少量配置。
- **⭐️⭐️⭐️**：**标准集成**。可以通过标准 GraphQL Server 集成到 Web 框架，但需要手动配置，需要中等配置。
- **⭐️**：**框架绑定**。强制绑定特定 Web 框架，无法集成到其他框架或需要大量手动适配。
